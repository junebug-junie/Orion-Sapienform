# Design: connect the golden seed concepts to the organic concept graph

Status: DESIGN ONLY — not implemented.
Arc: concept-atlas-graph-pipeline (2026-07-15 spec) → concept-atlas readability (2026-08-18 spec, PR #1754) → AI Town's own concept graph (PR #1760) → this doc.

## Arsonist summary

Orion and Juniper's golden seed nodes rank as top-degree "god nodes" in the Concept Atlas — and are also a fully isolated 3-node island, disconnected from every organically-discovered concept. `god_node` is a raw degree ranking with zero awareness of connected components, so it can (and does) crown a node that sits alone. The isolation isn't a bug in the god-node math; it's the absence of any mechanism that could ever connect these groups. This is not merely three arbitrary labels that would be nice to wire up: `services/orion-topic-foundry/app/pipelines/chat_corpus_builder/repository.py` builds topic-foundry's entire training corpus `FROM chat_history_log` — every organic topic/concept/entity in the graph is mined downstream of that one table. And `chat_history_log` rows are produced by exactly the identities the seed fixture represents: Juniper as the human speaker, Orion via `response_identity` on its own served-model turns (PR #1742), and — confirmed live, not design-only — Claude via `room_claude_relay.py`'s `room_claude_utterance` turns (invited over `orion:room:claude:request`/`orion:room:claude:utterance`, persisted into the same chat history as a distinct speaker). The seed nodes are the literal originating actors of the corpus the entire rest of the graph is downstream of, and they sit disconnected from it. The topic-foundry pipeline already resolves "this chat mentions a named entity" into a graph node (`EntityNodeV1`, via the `mentions` KG-edge feed) — it just never checks whether that entity is one of the chat's own root speakers. This design adds that check for all of them (Orion, Juniper, and Claude), plus fixes a pre-existing, related bug: entity nodes and their edges are silently invisible in the Concept Atlas UI today, seed-connection or not.

## Current architecture

Live-verified (`GET /api/substrate/concepts/network`, `orion_substrate` graph) as of 2026-08-19/20: 3 disconnected components —
1. Golden seed triad: `sub-concept-seed-orion`, `sub-concept-seed-juniper`, `sub-concept-seed-orion_juniper_relationship` (2 `associated_with` edges), written once by an operator-triggered route (`api_routes.py:308` → `orion.substrate.seed.load_seed_concepts_into_store`). Missing a 4th seat for Claude (see below) — the fixture predates `room_claude_relay.py`.
2. 9 degree-0 `node:substrate.<domain>` telemetry singletons, written by `_write_prediction_error_node()` in `services/orion-substrate-runtime/app/worker.py` — confirmed this function never calls `upsert_edge`. Active-Inference sensors, not organic concepts.
3. One organic topic-foundry concept cluster, connected internally via `supports`/`co_occurs_with` edges.

Root causes, confirmed by code (not inferred):

- **Identity resolution partitions by `node_kind`.** `SubstrateIdentityResolver.canonical_node_key()` (`orion/substrate/reconcile.py:105`) builds `concept|scope|subject|...` keys for concept nodes and a disjoint `entity|scope|subject|label:...` namespace for entity nodes (added 2026-07-28 specifically to dedupe entity nodes across ticks — never intended to reach across kinds). An `EntityNodeV1` labeled "Orion" can never identity-merge with the seed `ConceptNodeV1` labeled "Orion," by construction.
- **The seed nodes use a private identity key format.** `load_seed_concepts_into_store()` (`orion/substrate/seed.py:174`) writes with `identity_key=f"concept|{scope}|{subject}|seed"` — a format nothing else in the codebase generates (grep-confirmed). Structural isolation, not accidental.
- **The materializer already tolerates cross-record edges.** `SubstrateGraphMaterializer.apply_record()` (`orion/substrate/materializer.py:110-119`) resolves an edge's endpoint via `canonical_id_by_input_id.get(edge.target.node_id, edge.target.node_id)` — if the target isn't part of the current ingestion record, it passes the literal node_id straight through. An adapter can already emit an edge pointing at `sub-concept-seed-orion` without that node being part of the batch; it attaches correctly. **No materializer change needed.**
- **The real blocker is visibility, not storage.** `InMemorySubstrateGraphStore.read_concept_region()` (`orion/substrate/store.py:242-247`, the function every consumer of `query_concept_region()` ultimately calls) selects nodes with `node.node_kind == "concept"` only. Its edge selection then keeps any edge touching a selected node (OR), so a dangling edge to an off-slice entity node does survive this layer — but `concept_atlas_network()` (`services/orion-hub/scripts/concept_atlas_routes.py:1006-1007`) re-filters edges to **both** endpoints present in the (concept-only) node set (AND), silently dropping it. This already drops the pipeline's *existing* topic→entity `associated_with` mention edges today — a pre-existing, documented gap (`orion/substrate/adapters/topic_foundry.py`'s module docstring "Known limitation"), not something this design introduces.
- **`read_concept_region()`/`query_concept_region()` is a widely shared primitive** — also called from `reconcile.py`'s own embedding-candidate scan, `concept_induction_ctx.py`, `review_bootstrap.py`, `api_routes.py`'s substrate-semantic routes, `collectors/concept_region.py`, `seed_substrate_graphdb.py`. Widening its `node_kind` filter globally is out of scope for this patch — too broad a blast radius for a thin seam.
- **AI Town has no seed nodes.** `load_seed_concepts_into_store()` has exactly one caller (`api_routes.py:308`), which seeds `SUBSTRATE_SEMANTIC_STORE` (the Orion graph) — never `SUBSTRATE_SEMANTIC_STORE_AITOWN` (PR #1760's separate FalkorDB graph). There is nothing to connect to there.
- **`predicate` is a closed `Literal` enum** (`SubstrateEdgePredicateV1`, `orion/core/schemas/cognitive_substrate.py:24`) and `associated_with` is already a member, already used by both the seed fixture's own cross-links and the topic→entity mention edges. No schema change is required to reuse it here.
- **`anchor_scope` is also a closed `Literal` enum** (`SubstrateAnchorScopeV1 = Literal["orion", "juniper", "relationship", "world", "session"]`, same file, line 42) — unlike `predicate`, this one has no free slot for a fourth named-identity scope. Adding a Claude seed node in the same pattern as Orion/Juniper (its own dedicated `anchor_scope="claude"`, not lumped into `"world"`) genuinely requires widening this enum. Called out explicitly rather than silently decided — see Missing question 8 and Proposed schema changes.
- **`chat_history_log` is the corpus root, not an incidental source.** `services/orion-topic-foundry/app/pipelines/chat_corpus_builder/repository.py:26` selects `FROM chat_history_log` to build topic-foundry's entire training corpus — every organic topic, concept, and mentioned entity in the graph is downstream of that one table. Its rows are written by exactly three producers: Juniper as the human speaker; Orion via `response_identity` (`chat_history.py:323`, `turn_orchestrator.py:744`) on its own served-model turns; and Claude via `room_claude_relay.py`'s `RoomClaudeUtteranceV1` consumer, which pushes a frame into every live socket **and persists the turn** with its own `room_claude_utterance` kind so the UI renders it as a distinct speaker — confirmed live code, not the design-only state recorded from PR #1668. All three are already first-class, distinguishable identities in the very table topic-foundry mines.

## Missing questions

1. **Predicate**: reuse `associated_with` (matches the existing topic→entity semantic, zero schema change), or add a new predicate distinct enough for future typed-relation classification? — *Recommend reuse for patch 1.*
2. **Match strictness**: exact-normalized-label match only ("orion" / "juniper" / "orion-juniper relationship"), or alias/substring matching ("he", nicknames, "the operator")? — *Recommend exact match only for patch 1: deterministic, no regex swamp, no false-positive connections. Widen later only with real observed under-match data.*
3. **Hydration scope in `concept_atlas_network()`**: hydrate only entity nodes reached via a new landmark edge, or *every* off-slice node reachable from an edge in the current slice (which also resurrects the pre-existing topic→entity mentions as a free bonus fix)? — *Recommend the latter — same generic mechanism, fixes a real standing bug, bounded by a cap.*
4. **Do the 9 `node:substrate.<domain>` telemetry singletons get connected too?** — *Recommend explicitly no. Different node class (Active-Inference sensors never designed to have edges), different fix, would bundle two unrelated concerns into one patch. Flag as its own follow-up if wanted.*
5. **Does this apply to the AI Town graph (`?graph=aitown`)?** — *Recommend no. No seed nodes exist there; AI Town's organic townsfolk concepts have no natural Orion/Juniper landmark. Separate design question if Juniper wants AI Town agents to carry their own landmarks later.*
6. **Hydration cap**: how many extra off-slice nodes should `concept_atlas_network()` fetch beyond the existing 300-node concept limit? — *Recommend a small fixed cap (e.g. 100), matching this file's existing "generous but bounded" pattern.*
7. **Scope filtering interaction**: the seed nodes carry `anchor_scope` values `orion`/`juniper`/`relationship`; topic-foundry entities default to `anchor_scope="world"`. `concept_atlas_network()`'s `?scope=` filter runs *before* hydration today. Does a hydrated node need to independently satisfy an active `?scope=` filter, or is it exempt (it's reached structurally, via an edge, not by its own scope)? — *Recommend: hydrated nodes are exempt from `?scope=`/`?min_activation=` — they're structural context for an edge that already passed the filter, not primary query results. Document this explicitly in the route's docstring so it isn't mistaken for a filter bug later.*
8. **A fourth seed for Claude**: `orion/substrate/seed_concepts.yaml` predates `room_claude_relay.py` and only seats Orion/Juniper/their relationship — but Claude is now a real, live, distinct chat-history speaker (`room_claude_utterance`), one of the three actual producers of the corpus topic-foundry mines. Add a 4th entry (`key: claude`, `label: "Claude"`) so mentions of Claude in chat resolve to a landmark the same way Orion/Juniper mentions do. This needs its own `anchor_scope` — `"claude"` — which does not exist in `SubstrateAnchorScopeV1` today (unlike everything else in this design, this genuinely requires a schema-enum widening, not just wiring). Should it also carry `related_concept_keys: [orion, juniper]` (mirroring how `orion_juniper_relationship` links both ways), since Claude is invited into the room by either party (`room_claude_relay.py`: operator route *or* Orion's own auto-respond path)? — *Recommend yes: add `"claude"` to `SubstrateAnchorScopeV1`, add the 4th fixture entry with both relation links, and generalize `landmark_concept_ids` (already N-entries-generic, not hardcoded to 2) to cover it — no adapter code changes needed beyond the fixture.*

## Proposed schema / API changes

One real schema change (the Claude seed), otherwise pure wiring — no new node kind, no new `SubstrateEdgeV1` field, no env keys:

- **Schema**: widen `SubstrateAnchorScopeV1` (`orion/core/schemas/cognitive_substrate.py:42`) from `Literal["orion", "juniper", "relationship", "world", "session"]` to add `"claude"`. This is the one enum-widening in this design — flagged explicitly, not silently folded into "no schema changes." Grep every `SubstrateAnchorScopeV1` match-site (`_VALID_ANCHOR_SCOPES` in `concept_atlas_routes.py` and any other exhaustive-match code) before landing, so `?scope=claude` doesn't silently no-op the same way an unlisted value already logs-and-ignores today.
- **Fixture**: `orion/substrate/seed_concepts.yaml` gets a 4th entry — `key: claude`, `anchor_scope: claude`, `subject_ref: claude`, `label: "Claude"`, `related_concept_keys: [orion, juniper]` (Claude is invited by either party, per `room_claude_relay.py`). Produces `sub-concept-seed-claude` + two more `associated_with` edges via the existing loader — zero code change to `seed.py` itself, this file is pure data.
- `orion/substrate/adapters/topic_foundry.py::map_topic_foundry_run_to_substrate()` / `_build()`: new optional parameter `landmark_concept_ids: Mapping[str, str] | None = None` — normalized-lowercase label → an already-existing node_id. Generic over however many entries the caller passes (Orion/Juniper today, Claude added for free once the fixture has a 4th row) — not hardcoded to a fixed count. When a mention's normalized entity label exact-matches a key, emit one additional `SubstrateEdgeV1(source=NodeRefV1(entity_node_id, "entity"), target=NodeRefV1(landmark_node_id, "concept"), predicate="associated_with", ...)` alongside the existing topic→entity edge. Absent (default `None`) → zero behavior change for every existing caller (mirrors the resolver's own optionality pattern).
- `services/orion-hub/scripts/concept_atlas_routes.py::_ingest_topic_foundry_run()` (Orion-graph call path only — not the `_aitown` wrapper): build the landmark dict once per call via `orion.substrate.seed.load_seed_concept_nodes()` (pure/read-only, already separated from the write half; label.lower() → `f"sub-concept-seed-{key}"`), pass it through to the adapter call.
- `concept_atlas_routes.py::concept_atlas_network()`: after `nodes`/`edges` come back from `store.query_concept_region()`, add a bounded second pass — collect edge endpoint node_ids not already in the node set, resolve each via `store.get_node_by_id()` (already used elsewhere, e.g. `materializer.py`), append any found node to `nodes` up to the cap (missing question 6) — *before* degree/god-node/connected-component computation runs, so hydrated nodes participate in all three the same as any other node.

## Non-goals

- Not merging `EntityNodeV1`/`ConceptNodeV1` identity globally via `SubstrateIdentityResolver` — too invasive, silently changes identity semantics for every unrelated caller.
- Not connecting the 9 `node:substrate.<domain>` telemetry singletons — different node class, separate follow-up.
- Not extending this to the AI Town graph — no seed nodes live there.
- Not building alias/fuzzy/nickname matching — exact-normalized-label only for patch 1.
- Not widening `orion/substrate/store.py`'s shared `read_concept_region()` node_kind filter — blast radius too broad for a thin seam.
- Not inventing a new edge predicate/taxonomy entry.

## Acceptance checks

1. **Live**: after a topic-foundry run whose real mention edges include the literal text "Orion", "Juniper", and/or "Claude", re-run `concept_atlas_ingest_topic_foundry()`, then `GET /api/substrate/concepts/network` (default Orion graph) shows `sub-concept-seed-orion`/`sub-concept-seed-juniper`/`sub-concept-seed-claude` sharing `component_id` with the connected topic/entity cluster — not their current isolated singleton value.
2. **Unit** (adapter): `map_topic_foundry_run_to_substrate()` with a `landmark_concept_ids` dict (all 3 entries) and a mention whose `object == "Orion"` (and separately `"Claude"`) produces an edge from the entity node to the exact landmark node_id; a mention that does *not* match any landmark produces no extra edge (regression guard against over-matching).
3. **Unit** (route): `concept_atlas_network()`'s hydration pass includes an off-slice entity node reachable via an edge from an in-slice concept node, with correctly computed `god_node`/`component_id`/`degree` fields over the widened set — covers both the new landmark edges and the pre-existing topic→entity mentions.
4. **Regression**: existing `scope`/`min_activation`/`focus` filter tests in `test_concept_atlas_routes.py` pass unchanged; a test confirms hydrated nodes bypass `scope`/`min_activation` per missing-question 7's resolution.
5. **Cap**: a synthetic test with more dangling edges than the hydration cap confirms hydration stops at the cap rather than growing unbounded.
