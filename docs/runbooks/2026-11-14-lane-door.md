# Lane door: what a deploy does, check, roll back

Spec: `docs/superpowers/specs/2026-11-12-leased-evals-and-server-refusal-design.md` (Phases 2 and 3).
Service: `services/orion-lane-door/README.md`.

## What changes, plainly

Before the doors, every model server on circe listened on its lane port (chat 8011, fast 8013, agent 8015,
agent-gpu2 8016) for anyone athena let through. With the doors, a small "door" listens on that port
and passes each call to the engine. The engine moves to circe's own loopback (`127.0.0.1:180xx`). The door
writes down every model call that carries no lease id, i.e. did not come through the gateway. In shadow
mode it refuses nothing.

The GPU pool, the gateway and every caller keep using the same address and port.

There is no key and no secret. The gateway sends the lease id it already has (`X-Orion-Lease-Id`). The door
is there to catch Orion's own evals and scripts calling a model server by accident. It is not a fence
against a deliberate caller (see the spec, "Phase 2").

Cost on the call path: about 0.3-0.9 ms per call (`services/orion-lane-door/README.md`, "Cost").

## Deploy: nothing to do by hand

- **athena**: the post-pull rebuild rebuilds orion-llm-gateway (it now sends only the lease id).
  The doors never run on athena (`mesh-utilities/common/exclude_services.txt`).
- **circe**: the post-pull rebuild (`include_services_circe.txt`) does this, in order:
  1. `scripts/pre_rebuild.sh` creates `services/orion-lane-door/.env` from `.env_example` if it is missing.
  2. `up -d --build` starts the four circe doors. Each one waits: its engine still publishes the lane port.
  3. `scripts/post_rebuild.sh` runs `move_engines_behind_doors.py`. It recreates each RUNNING chat, agent
     and fast engine that still publishes its lane port. Compose now puts them on loopback. As soon as
     an engine answers on loopback, its door takes the lane port (within 2 s).
  4. agent-gpu2 is the GPU pool's. Its engine is not touched. Its door takes 8016 when the lane
     controller next unloads and loads the seat. The controller's `up` starts the engine on loopback.
     The seat is standby warm (never unloaded for idleness), so this can take days: the next swap, for
     example a diffusion lease on gpu2. Until then agent-gpu2 calls go straight to the old engine.
- **hecate**: `services/orion-vllm-host/scripts/hecate-deep.sh up -d` (the normal way to start agent-deep)
  starts the agent-deep door, then the engine on loopback (the door waits for it). `hecate-deep.sh stop` stops the door first.

What the FIRST circe deploy costs: the chat, agent and fast engines restart once, at the same time. Chat
and agent are Strata, which reloads its model in several minutes. Fast reloads in about a minute. While an
engine reloads, its lane is down: the pool sees the seat down, and Hub chat cannot answer until chat is
back. Pull circe at a quiet time for that first deploy.

Every later deploy: the engines are not touched. A change under `services/orion-lane-door/` recreates
the doors only. A recreated door stops taking new calls and lets calls in flight finish (up to 100 s).
New calls are refused at connect until the new door is up, normally a few seconds after the old one exits.

Does not need sudo. The circe port gate (`scripts/ops/circe_llm_port_gate.sh`) already covers the lane
ports. It covers a host-network listener the same as a docker-published port.

To keep one lane OFF the door (before or after a deploy), pin its engine to the lane port. The hook leaves
a pinned engine alone, and that lane's door just waits:

```bash
cd /mnt/scripts/Orion-Sapienform && echo 'ATLAS_CHAT_ENGINE_PUBLISH=8011' >> services/orion-llamacpp-host/.env
```

## Check (from athena, read-only)

```bash
for p in 8011 8013 8015 8016; do curl -s -m 3 http://100.112.254.99:$p/door/stats | python3 -c "import json,sys; d=json.load(sys.stdin); print(d['lane'], d['mode'], d['calls'])" || echo "$p: no door answering"; done
```

- `lane` is right and `mode` is `shadow`.
- After a few minutes `calls.leased` grows. `calls.unleased` and `calls.invalid` name what still calls
  around the gateway (`unleased_by_source`, `unleased_by_path`).
- A door that has not taken its port yet logs `lane_door_waiting` once a minute:
  `ssh circe@circe 'docker logs --since 10m orion-circe-lane-door-chat 2>&1 | tail -3'`.
- The Hub's GPU pool panel shows each seat up with recent grants (the pool's probes pass through the door).
- A Hub chat turn answers.

## The shadow evidence (daily, read-only)

```bash
ssh circe@circe 'cat /mnt/telemetry/lane-door/*.jsonl' | PGPASSWORD=postgres /mnt/scripts/Orion-Sapienform/.venv/bin/python scripts/lane_door_report.py - --dsn postgresql://postgres:postgres@localhost:55432/conjourney
```

Per lane per day: leased calls, unleased calls (and who sent them), invalid-lease calls, leased calls
whose lease id is not in `gpu_pool_events`, and the gateway's own count for that lane. The verdict line says
`READY TO ENFORCE` only after 7 complete UTC days in a row with zero unleased, zero invalid, every lease id
found, and the door's leased count within 1 % of the gateway's count. A day with no log is not a clean day.

The `overflow` column counts leases the gateway gave back on a context overflow and then re-leased for the same
request (#3942). Those leases have no gateway row of their own, so the gap compares distinct leases against
gateway rows plus this column. It comes from data that already exists: overflowed leases the door saw
(`gpu_pool_events` released with reason `context_overflow`) minus the lane's gateway rows with outcome
`context_overflow` (the request's last lease, when it also overflowed, carries that row). A lost gateway row
for an overflowed request can hide itself this way, but only for a lease the pool itself granted and recorded.

## Roll back one lane (on circe)

Put the engine back on its lane port, then stop its door:

```bash
cd /mnt/scripts/Orion-Sapienform && echo 'ATLAS_FAST_ENGINE_PUBLISH=8013' >> services/orion-llamacpp-host/.env && docker stop orion-circe-lane-door-fast && scripts/safe_docker_build.sh orion-llamacpp-host --compose-file docker-compose.atlas-workers.yml up -d --no-build --no-deps atlas-fast
```

Same shape for the other lanes (`ATLAS_CHAT_*` 8011 `atlas-chat`, `ATLAS_AGENT_*` 8015 `atlas-agent` with
`--profile agent-split`). A later deploy may start that door again; it then waits and never takes the port,
because the pinned engine does not answer on loopback. Lighter: set `LANE_DOOR_MODE_FAST=off` in
`services/orion-lane-door/.env` and recreate that door (pure pass-through).

## Notes

- The power bench (`scripts/gpu_power_bench.py`, run on circe as root) benches the engine on its loopback
  port (`--port 18016`). It refuses a lane door port.
- Loopback publishing keeps the engine reachable from circe itself only. circe's containers reach the
  engines by name on the docker network. The door covers callers from other machines, which is where the
  evals run.
- hecate's other agent-deep definitions (`docker-compose.hecate.yml`, the Strata challenger) still publish
  8021 themselves. Stop the deep engine with `hecate-deep.sh stop` first; that also stops the door.

## Phase 3: a lane's door refuses unleased calls (Juniper decides, one lane at a time)

The refusal is built and tested, and ships OFF: every door stays `shadow` until Juniper flips a lane.
The spec's rule: flip a lane only after its shadow data shows zero legitimate unleased callers.

### The evidence to look at first

Run the report above. For the lane you want to flip, all of these must hold:

1. The verdict line says `READY TO ENFORCE`, from a run WITH `--dsn` (the lease join ran). That means 7
   complete UTC days in a row, each with: unleased = 0, invalid = 0, leased > 0, every leased call's lease
   id found in `gpu_pool_events`, and the door's leased count within 1 % of the gateway's count for that lane.
2. The door's live counters agree: `curl -s http://100.112.254.99:<port>/door/stats` shows
   `calls.unleased = 0` and `calls.invalid = 0`.

If a lane shows unleased calls, the report names the source and path. Each one gets moved onto the lease
helper (`orion/evals/leased_llm.py`) or named in that lane's flip as a known holdout, before the flip.

Order (spec): agent-gpu2, then fast, then agent, then hecate agent-deep, then chat last.

### Flip one lane (on circe; no sudo)

```bash
cd /mnt/scripts/Orion-Sapienform && sed -i 's/^LANE_DOOR_MODE_FAST=.*/LANE_DOOR_MODE_FAST=enforce/' services/orion-lane-door/.env && scripts/safe_docker_build.sh orion-lane-door up -d lane-door-fast && sleep 5 && curl -s localhost:8013/door/stats | grep -o '"mode": "[a-z]*"'
```

`LANE_DOOR_MODE_CHAT` (port 8011), `_AGENT` (8015), `_AGENT_GPU2` (8016) the same way on circe. agent-deep
on hecate: the same `sed` with `LANE_DOOR_MODE_AGENT_DEEP`, then
`scripts/safe_docker_build.sh orion-lane-door --profile hecate up -d lane-door-agent-deep`.

### Check the flipped lane (from athena)

- A direct call is refused:
  `curl -s -o /dev/null -w "%{http_code}\n" -X POST http://100.112.254.99:8013/v1/chat/completions -H 'Content-Type: application/json' -d '{}'`
  reads `401`, and `/door/stats` shows `refused` grow by one.
- The pool's probes still pass: `curl -s -o /dev/null -w "%{http_code}\n" http://100.112.254.99:8013/health`
  reads `200`; the Hub's GPU pool panel shows the seat up with recent grants.
- Orion's own work still runs: `calls.leased` keeps growing; `refused` does not grow with it.
- For chat: a Hub chat turn answers. For agent-gpu2: a seat swap still completes (the ready probe is exempt).

### Roll back a flipped lane (seconds)

```bash
cd /mnt/scripts/Orion-Sapienform && sed -i 's/^LANE_DOOR_MODE_FAST=.*/LANE_DOOR_MODE_FAST=shadow/' services/orion-lane-door/.env && scripts/safe_docker_build.sh orion-lane-door up -d lane-door-fast
```

### kev :8009

kev gets no door (answer 7). `scripts/ops/circe_llm_port_gate.sh` lists 8009, so only athena reaches it. That
takes effect when the gate is re-installed on circe. A deploy cannot do this: the gate is a root-owned
systemd unit. This is the only sudo step, and the doors do not depend on it:

```bash
ssh -t circe@circe sudo /mnt/scripts/Orion-Sapienform/scripts/ops/circe_llm_port_gate.sh install
```

## Spike work on a pool card (rule from 2026-11-17)

A model loaded by hand next to a pool seat is invisible to the pool: no lease, no swap event. On 2026-11-16 and 2026-11-17 a test copy asked for GPU 3 by number and landed on GPU 2, Orion's second agent seat, leaving that card 342 MiB short of full.

1. Pin the card by its hardware id (`nvidia-smi -L` gives the UUID), never by index. Index order differs inside a container.
2. Before and after the window, print the card's memory (`orion_biometrics`, node circe, the GPU) and that seat's leases (`gpu_pool_leases`).
3. Stop at once if the memory rises on a card the spike did not ask for.
