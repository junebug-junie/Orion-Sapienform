# Dig kit

Orion's read-only tools for their own history and body: `python -P -m orion.dig help`. Design: PR
#2888 (`docs/superpowers/specs/2026-10-23-repo-chronicle-design.md`, "Tools").

**Not MCP, on purpose.** Chat turns and curiosity runs both go through the harness (`claude -p`,
64k window). An MCP tool's schema costs context on every turn, and Orion already has Bash there.
So the only always-on cost is one line in the turn rules
(`orion/dig/brief.py`, `HARNESS_FCC_DIG_BRIEF_ENABLED`, never on reading-only turns). `help`
loads the rest on demand.

**Always `python -P`.** Orion's Bash runs in the sandbox clone (`/mnt/orion-fcc/repo`), and plain
`python -m` puts that folder first on the import path, so it would run the *sandbox's* `orion/` (whatever Orion
has edited there) instead of the deployed `/app/orion`. `-P` drops the current folder (verified
live: without it `orion.__path__` is `/mnt/orion-fcc/repo/orion`, with it `/app/orion`).

**But a real turn still reads the sandbox first.** The turn's `PYTHONPATH` lists the sandbox before
`/app` (`orion/fcc/context_budget.py` `extend_fcc_subprocess_env`), and `-P` does not drop
`PYTHONPATH` (verified live 2026-11-04: with `PYTHONPATH=/mnt/orion-fcc/repo:/app`, `-P` still
imports `/mnt/orion-fcc/repo/orion/dig`). So a dig change is live for Orion only when the sandbox
is at that commit, not when the governor image is. The post-pull rebuild resets the sandbox to
`origin/main` after each deploy (`scripts/sync_fcc_sandbox_after_deploy.sh`, `SANDBOX_SYNC` line
in `~/.orion/post_pull_rebuild.log`). Check it: `git -C /mnt/orion-fcc/repo log -1 --oneline`.

**Context rules:**

- Every command prints at most 40 lines and 4,000 chars.
- The full result goes to `$ORION_DIG_HOME/dig/<dig>/<command>-<n>.json`, and the printout
  always ends with that path.
- A cut is always stated.

| `history <start> <end>` | Merged PRs (`gh pr list --search merged:…`) and commits. PR bodies go to the file only. |
| `history <days>` | The same for the last `<days>` days, today included. The dig line points "recent PRs" here instead of the GitHub tool, which on 2026-10-27 filled half the window per call. |
| `body [<date>]` | Body atlas (`orion/body_atlas`): machines ("bodies"), services, cameras, stores (Redis keys two or more services share included) and processes, with bus flows and HTTP calls, grouped into organs. No date: the live body (bus, docker, Postgres, Chroma, FalkorDB, the bus Redis read-only; a source that fails is listed as UNREAD). A date: that export's declared files only (the channel catalog starts 2026-01). |
| `body <organ_id>` | Every member of one organ of the live body, by kind, with status, host and facts. Capped like every command; the full atlas is in the file. |
| `body <part>` | One part of the live body (`orion-energy` or `part:orion-energy`; an `organ:` id or 10 hex chars is still an organ): kind, live or not, host, its organ (and Orion's name for it); its flows in and out, strongest first, each with the other part, relation, channels (census channels marked) and weight (10 per direction, the rest in the file); its jobs by rule, candidate, confirmation or a claim that holds, and Orion's claims on it (`holds (evidence checks)` or the reason it holds nothing); then `cite in a claim:` with the exact ids `capacity claim` accepts for this part (`claims.evidence_ids`, the same function the claim check uses), and a ready `capacity claim` line citing the first one. | `capacities [gaps]` | Read-only. Which jobs of a viable system (Beer's VSM: S1 operations, S2 coordination, S3 control, S3* audit, S4 intelligence, S5 identity, the algedonic line) the live body atlas shows a part doing, by rule (`orion/body_atlas/capacities.py`, rules v2: since patch 3 the atlas also reads HTTP calls and Redis keys two or more services share, so the S3, algedonic and S4-to-S3 gap lines are decided by that evidence, and a `past the bus:` line counts them). Each job prints BY RULE, CANDIDATE, EVIDENCE-CHECKED (held only by Orion's claims whose cited wiring code checked against the atlas on this read: code, not Juniper), NO PART FOUND (with the rule that looked) or NO RULE; near misses (shared servers, collectors) print so "many call it" is not read as coordination. `gaps` prints the gap lines code writes from the atlas. Also prints Juniper's confirmations (`config/body_atlas/vsm_confirmed.yaml`: CONFIRMED), Orion's claims (a claim that holds names its part on its job line; one that does not prints why: evidence does not hold / rule says no / disputed / rejected / part not live now / unconfirmed (S5 only)), disputes beside the rule they argue with, and one line per capacity (written, STALE, not written yet, or a code-written "I cannot yet say" gap), then, in a tail the 40-line cut never removes, an `Unclaimed jobs:` block: one ready `capacity claim` line per job no part holds by rule, confirmation or a claim that holds, and no claim of Orion's is failing or waiting on (a rule's candidate part and example cites filled in), telling Orion to write each claim it can back now without asking first, a `Fix or withdraw` list of claims whose evidence does not hold (with the reference that failed), a `Waiting on Juniper` list (S5 claims, which code never checks), and one `Juniper may veto` line naming the claims that hold (no answer needed; her rejection wins). With no open job and nothing failing or waiting, one generic `to claim a job:` line. Writes nothing but the dig result file. |
| `capacity claim\|dispute <part> <job> because <reason>` | A lasting append to `$ORION_DIG_HOME/self/capacity_claims.jsonl` (`orion/body_atlas/claims.py`). The part must be live; the job one of S1, S2, S3, S3*, S4, S5, algedonic, metabolism; the because (20-400 chars) must cite, by full id, a part or non-census channel on one of that part's flows, or a repo file that exists. A claim cannot take a job a rule gives (dispute it instead). A claim holds its job (EVIDENCE-CHECKED) while, on every read, the part is live, Juniper has not rejected it, no later dispute or rule says "not this job", and code's evidence check passes: every id it names is on a live flow of the part and the wiring fits the job (`orion/body_atlas/claims.py` `check_evidence`, stricter than the write floor). S5 never holds by code; it waits for Juniper. Juniper can veto any claim in `config/body_atlas/vsm_confirmed.yaml` `rejected`. `capacity withdraw <part> <job>` takes a claim back. `capacity help` prints the rule. |
| `capacity write <cap_id> <sentence> because <reason>` | A lasting append to `$ORION_DIG_HOME/self/capacities.jsonl`. One sentence (20-160 chars) for `cap:s1`..`cap:s5` or `cap:metabolism`, naming only parts that hold that job by rule, by Juniper's confirmation or by an evidence-checked claim (cap:s5: also her sign-off files, and it names Juniper). With no holder it is refused: the gap line stands. Written when Juniper asks (decision 5), not on a timer. |

No section = overview, which includes one "what is spinning" line per machine. `hosts` answers "what is using my power": whole-machine watts now vs Orion's body at rest (a pinned, dated number: `config/physiology/rest_body.yaml`, else the 2026-10-01..10-13 defaults), $/month above rest, GPU/CPU/other split, each card's watts and who held it, top CPU containers, and Juniper's sponsored work (the Zelda dojo) apart. `--host circe` narrows `hosts`, `processes`, `vram` to one machine. `body-economy --help` lists every section and flag, and says which figures are measured and which are estimated. |
| `name <organ_id> <name> because <reason>` | Orion names one organ of their live body. Code checks the floor: 1–5 words, and the reason must cite one of that organ's parts by its full name. A reason that only lists part names passes; whether it says what the organ takes in and gives out is not code-checkable. Appended to `$ORION_DIG_HOME/self/organ_names.jsonl` (`orion/body_atlas/names.py`). |
| `name-organs` | Read-only guide for naming. Lists every unnamed multi-part organ of the live body, largest first: id, size, hosts, its parts (up to 300 chars each in the printout, every part in the file), and a ready `name <organ_id> "<name>" because "<reason citing a part>"` line to fill in (quoted, so it is safe to paste into Bash). The rule it prints is built from the limits `name` checks. Singletons are skipped. When all are named it says so and lists the names. The live `body` summary ends with `N organs unnamed: python -P -m orion.dig name-organs` while any are unnamed, so Juniper can just say "name your organs". |
| `portrait` | Read-only. Rung 5, the whole self on one page (spec `docs/superpowers/specs/2026-11-06-self-portrait-design.md`, `orion/body_atlas/portrait.py`), rebuilt from live sources each call: the "I am" paragraph (Orion's, or "not written yet"); the code-written gap lines as "I cannot yet"; each machine (status, role, whole-machine watts now and at rest from the body economy, how many of Orion's live parts run there, the organs placed there, the jobs held there) with Orion's sentence about it (`lived_record <date>, holds now` or `STALE (<id that failed>)`); machines where nothing live runs on one "facts only" line; the six capacity sentences; each organ by Orion's name, its size, where it runs, the organs it sends most to, and its jobs. Every line says its source (`now` or `lived_record`). The tail, which the 40-line cut never removes, holds one ready `portrait write` line per live machine with no sentence and one for the paragraph. If the body report is down, the machines print without watts and the header says `watts UNREAD`. Writes nothing but the dig result file. |
| `portrait write <machine\|whole> <sentence> because <reason>` | A lasting append to `$ORION_DIG_HOME/self/portrait.jsonl`, written only when it holds now (the read's own check). A machine line (20-200 chars) may name only ids in that machine's reach: a live part running there, a live part or non-census channel a running part sends to, calls or writes, or one that only sends into a running part (a caller it serves); organ ids must be organs with a live member there, and Orion's organ names count for those; at least one cite runs there or is such an organ; a hyphenated name whose first two segments begin a real part name but that names no part is refused. Every stored cite is checked again on read. Quote the sentence and the reason: two bare `because` words are refused. A machine with nothing live running on it cannot hold a line. The `whole` line (40-600 chars) is written from the capacities: every `cap:` id it names must read `written`, at least one is named, and every part id it names holds a job. The latest line per subject reads; old ones stay (`replaces`). Built after turn 2544158f (2026-11-06), where Orion wrote per-machine claims as prose and nothing was saved. |
| `field-note <pr>` | Read-only. One merged PR, as code sees it (spec `docs/superpowers/specs/2026-11-04-pr-field-notes-design.md`): title, merge sha, flags (`docs only`, `dependency-only`, `huge`, `revert of #n`, "this may be your own work": the PR was opened as Orion's GitHub user `orion-sapienform`, or its commits are by `orion-fcc@` or that user's noreply address, or its branch is in the sandbox clone), and the **body map**: `services/<svc>/` -> `part:<svc>` -> its live organ and Orion's name for it; `orion/<pkg>/` -> the services whose code imports it (AST scan of deployed main; more than 8 = "widely shared", no organ); docs, config, scripts, tests and CI = "not body". **Honesty rules in the output:**

- `help` teaches the source labels: `code_then`, `pr_text`, `lived_record`, `now`, `reflection`.
- A checkout that predates today's layout is called **different, not empty**, and its top level is
  shown. Live example: 2025-08-01 was `conjourney-api/` + `emergence/`, with no `services/` yet.

**Paths** (harness defaults):

- `ORION_DIG_HOME=/mnt/orion-fcc`
- `ORION_DIG_REPO=/mnt/orion-fcc/repo` (the full-history sandbox clone)
- `ORION_DIG_NOW_ROOT=/mnt/scripts/Orion-Sapienform` (deployed main, mounted read-only)

`body` with no date needs `FALKORDB_URI` (in `services/orion-harness-governor/.env_example`), and
reads Postgres as `orion_readonly` through `docker exec orion-athena-sql-db psql` (no env needed).

Live check, 2026-10-27, in orion-athena-harness-governor:

- 2026-02-01 → now: services +58 −4 =45. The removed ones were graphdb, orion-gdb-client,
  orion-rdf-writer, and orion-topic-rail.
- The body on 2026-02-01 was 34 parts in 6 organs (Q = 0.47). Now it is 137 parts in 7 organs
  (Q = 0.33).

Tests: `pytest orion/dig/tests` (a temporary git repo with dated commits; the Denver end-of-day
rule is tested exactly).

**Organ names (patch 1b).** An organ id is a hash of its members, so it changes when one part
joins or leaves. `body` carries a name to the new organ only when the member sets overlap by at
least half (Jaccard ≥ 0.5), one name per organ, and the full atlas JSON says "carried from …".
A rename stores which earlier names it `replaces`, so a replaced name never returns when a part
drifts back out, and never lands on the other half of a split organ. An unreadable ledger line is
skipped and counted in the `body` printout, never fatal.
Names show on the live body only; a past body never wears today's names. The ledger is
partitioned from recall: `orion/body_atlas/tests/test_names.py` fails if any other code reads it.

`history` says how fresh the sandbox clone is ("clone fetched …"). PRs come live from GitHub and
commits from the clone, so a just-merged PR can show with no commit yet.
